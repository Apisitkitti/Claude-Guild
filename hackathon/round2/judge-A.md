# Judge A รอบ 2 — กรรมการสายผลิตภัณฑ์

**มุมมอง:** นักพัฒนาที่เปิด Claude Code หลาย session พร้อมกันแล้วเปิดกิลด์ทิ้งไว้ ฟีเจอร์นี้เปลี่ยนวิธีทำงานในแต่ละวันไหม และพอหายตื่นเต้นแล้วยังจะใช้ต่อไหม

**สูตร:** Total = 2×Impact + Delight + Feasibility + Theme + Risk (เต็ม 60, Risk 10 = เสี่ยงต่ำ)

## สิ่งที่ตรวจกับโค้ด

- `store.ts:249` `DROP_KEYS` ทิ้ง `tool_response` และ `last_assistant_message` ตั้งแต่ใน `addEvent` จริง ทีม 1 (hash response) และทีม 3 (อ่านท้ายข้อความ Stop) จึงต้องอ่านค่าจาก `raw` ก่อนถึงลูป DROP ทำได้ แต่ต้องแก้ตรงนี้ ไม่ใช่ข้อมูลที่ "มีอยู่แล้ว" ใน event ที่เก็บไว้
- `slim` ตัด string ที่ 300 ตัวอักษร (`store.ts:234`) ทีม 4 อ้างถูก แต่ fingerprint ของ Edit ตามแบบทีม 3 (`hash(old_string)`) ต้องคิดจาก raw ไม่ใช่จากค่าที่ slim แล้ว ไม่งั้น Edit ที่ต่างกันหลัง 300 ตัวอักษรจะกลายเป็น hash เดียวกัน
- `app/events/route.ts` มี `MAX_BODY = 1MB` และ hook ใช้ `curl --max-time 1` ถ้า PostToolUse ที่ response ใหญ่ได้ 413 กลับมา event นั้นจะหายทั้งตัว คนที่อาศัยขนาด response (ทีม 2) จะพลาดตัวที่ "กินมานา" มากที่สุดพอดี
- `transcript.ts` อ่านแค่ tail 256KB แล้วคืน usage ล่าสุด (`:75-83`) อนุกรมแบบที่ทีม 2 ต้องการจึงต้องเปลี่ยนเป็นการอ่านต่อจาก offset เดิม ซึ่งเป็นงานที่ใหญ่กว่า "ขยาย readContext" อย่างที่ pitch บอก
- hook ทั้ง 12 ตัวเป็น `async` + `|| true` และมี `PreCompact` / `Notification` / `PostToolUseFailure` ลงทะเบียนอยู่จริง ทุกทีมระบุไว้แล้วว่า "เตือนได้ แต่ขวางไม่ได้" ซึ่งถูกต้อง
- `waiting` (`store.ts:217`) ไม่มี hook ตอนกด approve (README:72) ⏳ "รอคุณ > 5 นาที" ของทีม 4 และคิว permission ของทีม 3 จึงอาจค้างนานเกินจริง
- มี `app/health/route.ts` อยู่แล้ว ถ้าทีม 4 ตั้งชื่อไฟล์ว่า `lib/health.ts` จะสับสนกับ health check ได้ ควรตั้งชื่อเป็น `lib/infirmary.ts`

## คอมเมนต์รายทีม

### ทีม 1 — Berserk Watch (46)
- **จุดแข็ง:** ตัวตรวจแม่นที่สุดในสามทีมที่จับลูป เพราะใช้เงื่อนไข "input เดิม **และ** ผลเดิม" (ผลเปลี่ยนแปลว่ายังคืบหน้า) ช่วยกัน false positive ได้ตรงจุด ภาพตาแดง + Rage meter เป็นสัญญาณจริงที่อ่านได้จากระยะไกลโดยไม่ต้องอ่านตัวหนังสือ ซึ่งเข้าธีมที่สุด
- **จุดอ่อน:** แก้ได้ปัญหาเดียว พอผ่านไป 30 วัน ส่วนใหญ่ตัวละครจะไม่คลั่ง ฟีเจอร์ก็แทบมองไม่เห็น ต้องวาด sprite ใหม่ทุกคลาส ทำให้ขอบเขตงานบวมขึ้น
- **ต้องแก้:** hash ของ `tool_response` ต้องคิดจาก `raw` ก่อน `DROP_KEYS` และถ้า response ใหญ่จนโดน 413 ให้ถือว่าเป็น "ไม่ทราบผล" ไม่นับว่าซ้ำ

### ทีม 2 — Mana Ledger (40)
- **จุดแข็ง:** เป็นทีมเดียวที่ทำนายล่วงหน้าได้ ("อีก ~14 turn ถึง compact") และการจับ cache หลุดหลังพักนานคือข้อมูลเรื่องเงินจริงที่ dev ไม่เคยเห็นมาก่อน ทุกตัวเลขมาจาก usage จริง ไม่มีค่าสุ่ม
- **จุดอ่อน:** เป็น panel DOM ล้วน ไม่แตะกิลด์เลย คนจะเปิดดูเฉพาะตอนสงสัย ไม่ได้ดูทุกวัน การแบ่ง token ให้แต่ละ tool call เป็นการประมาณที่ dev อาจไม่เชื่อ และต้องเขียน parser transcript ใหม่แบบ incremental
- **ต้องแก้:** ตัด "ตัวกินมานา Top 5" ออกจาก MVP ให้เหลือแค่ badge พยากรณ์บนการ์ดกับ toast cache หลุด ถ้าจะทำ attribution ให้ใช้ความยาว `tool_result` ใน transcript แทน hook ที่อาจโดน 413

### ทีม 3 — Lookout Bell (47)
- **จุดแข็ง:** ตอบคำถามที่คนรันหลาย session ถามตัวเองวันละหลายสิบครั้งว่า "ควรไปดู session ไหนก่อน" รวม permission / ลูป / ถามกลับ / context / เสร็จแล้ว ไว้ในคิวเดียว และมีปุ่ม `N` ไปตัวถัดไป ใช้ได้ทุกวันไม่ว่าจะมีปัญหาหรือไม่ จึงไม่จางหายไปตามเวลา ตัวตรวจ "Claude ถามกลับแต่ดูเหมือนเสร็จแล้ว" เป็นปัญหาจริงที่ไม่มีทีมอื่นจับ
- **จุดอ่อน:** ธีมบางที่สุด (เป็นคิว HTML บวกไอคอนเหนือหัว) heuristic ที่เช็ก `?` / "Should I" เดาผิดได้ง่าย และตัวตรวจลูปตัดสินแค่จาก "ล้มเหลว" ซึ่งหยาบกว่าการเทียบผลแบบทีม 1
- **ต้องแก้:** ให้คลิกในคิวแล้วกล้องเลื่อนไปที่ตัวละคร พร้อม animation "ยามสั่นกระดิ่ง" บน canvas เพื่อดึงธีมกลับมา และเอาเงื่อนไข "ผลเดิม" ของทีม 1 มาใช้ในตัวตรวจลูป

### ทีม 4 — Infirmary (41)
- **จุดแข็ง:** ภาพนักบวชวิ่งไปร่ายเวทใส่ตัวที่ป่วยน่ารักและสื่อความหมายได้ ใบวินิจฉัยพร้อมปุ่ม Copy ใช้ได้จริง รับข้อติจากรอบ 1 มาครบ (ตรวจฝั่ง server, `tool_use_id`, ไม่โฆษณาเกินจริง)
- **จุดอ่อน:** มีตัวตรวจ 6 ตัวในรอบเดียว แต่ละตัวจึงตื้น ป้ายชวนพักสำหรับคนคือส่วนที่ dev จะปิดทิ้งเป็นอย่างแรก ส่วน regex คำสั่งเสี่ยงก็คือ Wards รอบ 1 ที่ย้ายมาอยู่ตรงนี้ และจับได้หลังเกิดเหตุไปแล้ว
- **ต้องแก้:** ตัดข้อ 5 และ 6 ออก เหลือแค่ Loop / Failure / Context / รอคุณ และเปลี่ยนชื่อไฟล์เป็น `lib/infirmary.ts`

## ความซ้ำซ้อน: ทีม 1, 3, 4 ทำตัวจับลูปเหมือนกัน
- **ตัวตรวจที่ดีที่สุด:** ทีม 1 (fingerprint + response hash, รีเซ็ตเมื่อ `UserPromptSubmit`/`Stop`)
- **กรอบคิดที่ดีที่สุด:** ทีม 3 ที่มองว่าลูปเป็นแค่ "เหตุผลหนึ่ง" ในคิวความสนใจ ไม่ใช่ฟีเจอร์เดี่ยว แบบนี้ dev เปิดใช้ทุกวัน ไม่ใช่เฉพาะวันที่มีปัญหา
- **ภาพที่ดีที่สุด:** Rage meter ของทีม 1 กับนักบวชของทีม 4 แต่ควรเลือกอย่างเดียว
- **ควรรวมเป็นฟีเจอร์เดียว:** ทำ `lib/attention.ts` ฝั่ง server ตัวเดียว (โครงจากทีม 3 + ตัวตรวจลูปจากทีม 1 + ใบวินิจฉัยและปุ่ม Copy จากทีม 1/4) แล้วแสดงบน canvas ด้วยภาพแบบเดียว ห้ามสร้างตัวตรวจ 3 ตัวที่เตือนเรื่องเดียวกันซ้ำกัน
